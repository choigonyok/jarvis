# calendar-svc

일정의 **저장만** 여기 있습니다. 승인 카드·MCP 도구 스키마·되돌림 가능 여부는
agent 에 남아 있습니다.

## 저장소: uniple

일정은 **uniple**(커플 앱)의 공유 캘린더에 있습니다. `CALENDAR_BACKEND=uniple`
일 때 이 서비스는 Postgres 표 대신 uniple 의 Supabase(`api.uniple.app`)를
로그인한 사용자 자격으로 호출합니다. API 계약은 그대로라 agent 와 웹은 바뀐
것을 모릅니다. `postgres` 로 되돌리면 예전 표(`commitments`, 기존 6개 그대로)를
씁니다.

- **비공식입니다.** uniple 은 공개 API 가 없고, 표·컬럼 이름은 앱 번들에서 읽었습니다.
  앱이 바뀌면 깨지며, 그때는 빈 캘린더가 아니라 오류로 드러납니다.
- **로그인 토큰은 쓸 때마다 회전합니다.** 환경변수 `UNIPLE_REFRESH_TOKEN` 은 씨앗일
  뿐이고 살아 있는 값은 `uniple_session` 표에 있습니다. 로그인이 풀리면 시크릿 창에서
  다시 로그인해 새 토큰을 환경변수에 넣고 재시작하면 됩니다(씨앗이 바뀌면 그쪽을 따름).
- **공유 캘린더입니다.** 쓰기는 상대방 휴대폰에 바로 보입니다. 새 일정은 승인 카드로만
  들어오고(agent 의 `POST /calendar` 는 새 일정을 403 으로 거절), 알림은 걸지 않습니다.
- **반복 일정**은 앱의 펼치기 로직을 그대로 옮겼습니다(`internal/uniple/expand.go`).
  하루치의 id 는 `시리즈#날짜` 이고, 그 하루를 지우면 시리즈의 예외 날짜로 들어갑니다.
  하루만 수정하는 것은 앱에서 합니다.
- `owner` 는 me | partner | shared 로 *누구의 일정인지* 표시할 뿐 숨기지 않습니다.
- 장소는 칸을 따로 두지 않고 메모에 적습니다. 쓰는 쪽이 장소를 따로 넘겨도 저장할 때 메모 첫 줄이 되고
  (`event.Validate`), 메모에 이미 있으면 그대로입니다. 예전 일정의 첫 줄 `📍 장소` 는 읽을 때만 장소로
  풀리고, 다음에 저장할 때 평범한 메모가 됩니다.
- 기간이 비면 앞뒤 1년으로 자릅니다. 매일 반복하는 일정에는 끝이 없기 때문입니다.

## 경계를 여기에 그은 이유

앞의 두 서비스와 다릅니다. 운동과 자산은 데이터와 그것을 읽는 방법이 전부
옮겨왔지만, 캘린더는 쪼갰습니다.

| 있는 곳 | 무엇 |
|---|---|
| agent | 승인 카드(`Preview`), 도구 스키마, `Reversible` 선언, SSE 발행 |
| calendar-svc | 일정 저장, 기간 조회, 충돌 검사 |

카드와 도구 정의는 **대화와 게이트의 속성**입니다. 여기로 옮기면 하나의
결정이 두 프로세스에 걸쳐 쪼개집니다 — 무엇을 승인받을지 아는 쪽과 승인을
기다리는 쪽이 달라지면, 승인 흐름이 네트워크를 한 번 더 건너게 됩니다.

이 서비스는 시키는 대로 합니다. 여기 도달한 쓰기는 **사람이 직접 친 것이거나
사람이 승인한 것**입니다.

덤으로 원래 목적이 더 확실해졌습니다. 캘린더 파일을 워크스페이스 바깥에 둔
이유는 CLI 의 `Read`/`Write` 도구가 모듈의 스키마와 승인 카드를 우회하는 두
번째 문이 되는 것을 막기 위해서였습니다. 이제 에이전트의 파일시스템에 캘린더가
**아예 없습니다.**

## API

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/health` | Postgres 를 ping 합니다. 토큰 불필요 |
| GET | `/events?from=&to=` | 기간 조회. 양끝 포함, 빈 값은 무제한 |
| GET | `/events/{id}` | 하나 |
| PUT | `/events` | id 없으면 추가, 있으면 수정 |
| DELETE | `/events/{id}` | 삭제 |
| GET | `/events/{id}/conflicts?buffer=30m` | 겹치는 확정 일정 |

`PUT /events` 와 `PATCH /events/{id}` 는 화면의 일정 양식이 고른 것만 받는다: `repeat`(none·daily·weekly·biweekly·monthly·yearly)
와 `reminder`(시작 몇 분 전, -1 은 끔)가 없으면 반복과 알림을 건드리지 않는다. 대화와 카드가 보내는 일정은 둘을 보내지 않으니
새 일정에는 반복도 알림도 없고, 고친 일정은 있던 그대로다. 읽을 때 `reminder` 는 걸린 알림(분)이다.

## 커플 공간의 나머지

uniple 의 홈은 캘린더 말고도 블록이 있다: 디데이, 버킷리스트, 습관 체크, 데이트 지도, 자유 블록, 그리고 사진·일기·가계부 같은
것들. 같은 세션(회전하는 토큰은 이 프로세스 하나가 쥔다)으로 앱이 읽는 표를 앱처럼 읽고, 앱이 쓰는 칸만 쓴다. 표와 칸은 앱
번들의 블록 정의(`itemTable`·`itemSelectColumns`)와 쓰기 코드에서 읽었다. uniple 이 아닐 때(`CALENDAR_BACKEND=postgres`)는 404,
손님 토큰은 403 이다(세션이 운영자 것이라 손님의 체크가 운영자 이름으로 들어가게 된다).

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/couple` | 두 사람(별명), 만난 날(`spaces.anniversary_date`), 주의 첫날, 홈의 블록과 그 항목. 지도는 지역마다 대표 사진 하나 |
| GET | `/couple/blocks/{id}` | 블록 하나. 지도는 사진 전부와 기록 |
| GET | `/couple/blocks/{id}/checks?from=&to=` | 습관 블록의 두 사람 체크 |
| GET | `/couple/news?limit=` | 공간에서 한 일(앱의 알림 목록), 그 항목의 지금 모습과 함께 |
| GET | `/couple/photos?from=&to=` · `/couple/cover?date=` | 캘린더 날의 사진, 캘린더 카드가 보이는 사진 |
| GET | `/couple/media/{asset}?size=thumb\|display` | 사진 한 장(공개 저장소에서 받아 그대로, 브라우저 캐시 7일) |
| POST · PATCH | `/couple/blocks` · `/couple/blocks/{id}` | 블록 추가(버킷·습관·자유, 앱과 같은 개수 한도) · 이름 바꾸기 |
| POST · PATCH · DELETE | `/couple/blocks/{id}/dday[/{item}]` | 기념일. 바꾸면 `sync_dday_calendar_events` 로 캘린더의 기념일 일정도 다시 쓴다. 만난 날은 앱에서 |
| POST · PATCH · DELETE | `/couple/blocks/{id}/bucket[/{item}]` | 버킷(맨 뒤에), 이룸·이름, 지우기 |
| POST · DELETE | `/couple/blocks/{id}/free[/{item}]` | 자유 블록의 기록 |
| POST · PATCH · DELETE | `/couple/blocks/{id}/checks[/{item}]` | 내 체크(오지 않은 날은 거절, 같은 날 두 번은 하나), 메모, 취소 - 내 것만 |
| POST · PATCH · DELETE | `/couple/blocks/{id}/records[/{item}]` | 데이트 지도의 기록. 서울의 구는 앱처럼 `S01`~`S25` 로 쓰고 다섯 자리로 읽는다. 사진이 붙은 기록은 지우지 않는다(사진 파일 정리는 앱이 한다) |

사진 올리기는 하지 않는다: 앱은 자기 서버(`/api/media/uploads`)에서 서명한 주소로 올리고 RPC 로 마무리하는데, 그 서버는 쿠키
세션으로만 열린다. 쓰기는 모두 mind 의 문(`/api/couple/...`)과 손(output 의 허용 목록)을 거쳐 온다.

## 벽시계가 진실입니다

`date` + `start`/`end` 를 문자열로 저장합니다. 한 시간대에서 쓰는 개인
캘린더에서 "19:00"을 적고 "19:00"을 읽는 것이 옳고, timestamptz 로 왕복시키면
입력한 문자가 달라져 보일 여지만 생깁니다.

충돌 검사는 구간 연산이라 정확해야 하므로, `span` 을 **트리거가 파생 컬럼으로**
채웁니다. 시간대는 데이터베이스에 박혀 있습니다(`jarvis.timezone`).

**`span` 을 직접 쓰지 마세요.** 두 곳에서 계산하면 언젠가 갈라집니다.

- 종일 일정은 `span` 이 NULL 입니다. 하루를 다 막으면 그날의 모든 시간 약속이
  충돌로 잡히고, 그건 "생일"이 "회의"와 겹친다는 뜻이 됩니다.
- 끝시각이 없으면 1시간으로 가정합니다. 추측이지만, 구간이 없으면 충돌 검사에서
  통째로 빠져서 "19시에 약속"이 아무것과도 겹치지 않는다고 답하게 됩니다.

## 겹침을 막지 않습니다

배제 제약을 걸지 않았습니다. 일부러 겹쳐 잡는 일정이 있고(옮길지 고민 중인 두
후보), 사람이 직접 쓰는 경로는 결재를 거치지 않기로 한 제품입니다. 여기서
INSERT 를 거부하면 캘린더 UI 가 고장납니다.

겹침은 막을 일이 아니라 **알아차려서 제안할 일**이므로 `/conflicts` 가 있습니다.

`buffer` 는 이동시간입니다. 19시 강남과 20시 판교는 겹치지 않지만 둘 다 갈 수는
없고, 여유를 넣고 보는 것이 그것을 알아차리는 유일한 방법입니다. 기본값이 0인
이유는 이동시간을 모르는 채 30분을 가정하면 붙여 잡은 일정마다 충돌이라고 말하게
되기 때문입니다.

## 검증을 두 곳에서 합니다

중복이 아니라 위치의 문제입니다.

- **agent**: 모델이 상대 날짜("다음 주 화요일")를 보냈을 때 왕복 없이 즉시
  거부되고, 그 거부가 도구 호출의 결과로 모델에게 전달됩니다
- **여기**: 이 에이전트를 거치지 않는 두 번째 쓰기(웹의 직접 편집, 나중의
  임포터)를 막는 실제 관문

## 기존 일정 옮기기

(옮기기는 끝났고, 이 일회성 `calendar-import` 서비스와 스크립트는 지웠습니다. 아래는 그때의 기록입니다.)

에이전트 볼륨의 `/data/calendar.json` 을 하나씩 PUT 합니다. id 를 그대로 보내므로
여러 번 돌려도 같은 결과입니다. **원본은 지우지 않습니다.**

## 검증한 것

실제 데이터로 컨테이너에서 확인했습니다.

- 기존 `calendar.json` 6개가 전부 옮겨지고, 벽시계가 그대로 보존됨
- 파생 구간이 KST 로 계산됨. 종일 일정 3개는 `span` 이 NULL
- 기간 조회가 양끝을 포함하고, 종일 일정이 그날의 맨 위에 옴
- 충돌: 뒤풀이(21–23)가 합주(19–22)를 잡음. 붙어 있는 귀가(23–24)는 여유
  0분에서 안 잡히고 30분에서 잡힘. 자기 자신은 빠짐
- 상대 날짜와 거꾸로 된 시각이 사람이 읽을 메시지와 함께 400
- 없는 id 삭제는 404
- agent 의 `/calendar` 조회·추가·삭제가 이 서비스를 통과함
- agent 의 `look` 도구(`calendar`)가 이 서비스에서 읽어옴 (핸드셰이크 후
  `tools/call` 로 확인)
- 에이전트 테스트 전체 통과 — 캘린더 테스트는 가짜 서비스를 띄워 Postgres 없이
  돌아갑니다

## 고친 것

**23시 이후에 시작하고 끝시각이 없는 일정을 저장할 수 없었습니다.**

끝시각이 없을 때 1시간을 더하는 계산을 `time` 공간에서 했는데, `time` 의 덧셈은
자정에서 되돌아갑니다.

```sql
select time '23:00' + interval '1 hour';   -- 00:00:00
```

구간이 `[23:00, 00:00)` 이 되어 하한이 상한보다 커지고, `tstzrange` 생성 자체가
거부됐습니다(SQLSTATE 22000). 시작 시각이 23:00~23:59 일 때만 터지므로 낮
시간대만 써보는 동안은 드러나지 않았습니다.
[016_fix_late_night_span.sql](../db/migrations/016_fix_late_night_span.sql) 이
타임스탬프 공간에서 더하도록 고칩니다.

남는 제약: 23:00 에 시작해 01:00 에 끝나는 **자정을 넘는 일정**은 여전히 넣을 수
없습니다. `end_time >= start_time` check 가 막고, 그건 파일 저장소 시절의 규칙을
그대로 옮겨온 것입니다. 하루 안에서 끝나지 않는 일정을 어떻게 적을지는 저장
방식이 아니라 제품의 결정이라 바꾸지 않았습니다.
