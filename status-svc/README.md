# status-svc

상태 탭의 판정. "뭐가 고장났나"를 컨테이너가 아니라 기능 단위로 답한다.

## 경계

**읽기만 한다.** 판정은 대부분 이미 있는 신호로 한다:

| 신호 | 어디서 |
| --- | --- |
| 수집기 루프, 마지막 메시지 시각 | kakaotalk `/status`, `/messages/recent` |
| 카드 알림 수신, 읽지 못한 알림 | spending `/spending` 의 `collector`, `unparsed` |
| 증권사별 실패 | assets `/portfolio` 의 `problems` (10분에 한 번, 네 항목이 공유) |
| uniple 접근 | calendar `/events?from=오늘&to=오늘` (5분에 한 번) |
| 쿠팡 주문목록 접근 | 에이전트 브라우저 새 탭에서 직접 열어 보고, 로그인 화면으로 넘어가는지 (30분마다) |
| 네이버페이 주문내역 | 조회 기록만. 결제 감시가 pay.naver.com 요청을 GET 까지 결재 카드로 세우므로 열지 않는다 |
| 상품 상세 조회 대기·로그인 대기 | `card_transactions.enrich_status` |
| 자산 일별 기록 | `portfolio_snapshots.taken_at` |
| 서비스마다 반복 작업의 진행, 격리함 | 각 서비스의 `/health`(아래 '서비스의 계약') |
| 이벤트 로그의 구독자별 전달 | events `/health` 의 `deliver:<소비자>` |
| iMessage 수집기 | imessage `/status` |
| 목소리·그림 속 글자 읽기(맥미니 호스트) | `host.docker.internal:8106`·`8107` 의 `/health` |
| 사진·기억 그래프 | immich `/api/server/ping`, FalkorDB 에 `PING` |
| 매일 백업의 내용 | 그날의 `manifest.json` 에서 빠진 것(host-check 가 옮겨 적음) |

**소모하는 감시는 하지 않는다.** uniple 리프레시 토큰은 쓸 때마다 회전하고 KIS
토큰은 1분에 하나만 발급된다. 그것을 직접 두드리는 헬스체크는 감시 대상을
망가뜨리는 원인이 된다. 캘린더 확인이 쓰는 액세스 토큰은 calendar-svc 가 원래
하던 대로 한 시간에 한 번 갱신한다.

**주문목록 접근은 직접 열어 본다.** 처음에는 프로필의 쿠키로 판단했는데, 쿠팡
쿠키가 모두 살아 있는데도 주문목록이 로그인 화면으로 넘어갔다. 그래서 에이전트가
쓰는 그 브라우저로 새 탭을 열어 도착한 주소를 보고, 탭을 닫고, 원래 탭으로
초점을 돌려준다. 이미 로그인 화면이 열린 탭이 있으면 열지 않는다 - 누가 비밀번호를
치는 중일 수 있다. 같은 브라우저를 에이전트도 쓰므로 30분에 한 번만 연다.

**측정하지 않는 것.** Claude Code 구독 인증은 에이전트가 실패를 저장하지 않아서
"측정 안 함"으로 둔다.

## 서비스의 계약

서비스는 `GET /health` 를 같은 모양으로 답한다([`gocommon/health`](../gocommon/health/health.go)):
`loops` 는 반복 작업마다 마지막으로 끝까지 돈 때·마지막 오류·연달은 실패·기다리는 가장 오래된 것,
`held` 는 격리함(실패를 거듭해 따로 둔 것)의 수·가장 오래된 것·몇 개의 이름과 이유·처리할 곳이다.
이전 모양(`{"status":"ok"}`)도 그대로 읽는다.

- 서비스의 줄(기반): 200 이고 반복 작업이 저마다 정한 시간 안에 한 번은 끝까지 돌았으면 정상, 그 시간을
  넘기면 이상(멈춤), 세 번 넘게 연달아 실패하는 중이면 주의. 반복 작업은 할 일이 없어도 한 바퀴가 끝나면
  "돌았다"고 적으므로, 실패하지 않고 멈춰 버린 것도 시간이 지나면 이상이 된다.
- 격리함의 줄(격리함): 따로 둔 것이 없으면 정상, 있으면 주의 - 그 목록과 처리할 곳을 펼친 줄에 보인다.
  가계부(읽지 못한 카드 알림), 이벤트(전하지 못한 이벤트), 기억(넣지 못한 사실), 작업(멈춘 작업).
- 이벤트 로그는 받는 쪽마다 줄이 따로다(이벤트 → 알림·에이전트·mind). 받는 쪽이 꺼졌으면 원인으로 그쪽을 가리킨다.

같은 `/health` 를 여러 줄이 읽으므로 10초 동안 한 번만 읽고, 주소마다 따로 기다린다(느린 서비스가 다른
줄을 붙잡지 않게).

## 원인 연결

각 항목은 `Deps` 를 선언한다. 자신이 이상이고 의존 대상도 이상이면, 가장 깊은
이상 항목을 `cause` 로 돌려준다. 화면은 그것을 "X 때문일 수 있어요"로 적고,
맨 위 문장은 원인이 없는 이상만 센다. 카톡이 꺼져서 카드 알림도 멈춘 것은
한 가지 문제다.

## API

| | |
| --- | --- |
| `GET /health` | 프로세스가 떠 있으면 200 |
| `GET /status` | 항목별 최신 판정 |
| `POST /refresh` | 지금 다시 확인하고 결과를 돌려줌. 느린 항목은 최소 간격을 지킨다 |

항목 추가는 `internal/probes/probes.go` 의 `All` 에 한 줄.
